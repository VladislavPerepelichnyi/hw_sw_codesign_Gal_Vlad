# btree benchmark — analysis, optimization and hardware acceleration

All deliverables for the pyperformance `btree` benchmark: measurements, the
optimized benchmark, the SystemVerilog Node Search Unit, the report and the
prompt log. The repository is self-contained: both versions of the benchmark code are
committed under `Hw__Additional_Files/benchmark/`, and every stage and script
reads them from there. pyperformance is installed only as the harness (pinned
to 1.14.0); nothing is taken from the benchmark copy inside that package.
Everything runs relative to this directory; no path depends on the user's home.

Hardware counters inside a virtual machine are only partly virtualised: KVM
exposes cycles, instructions and the L1/L2 events to the guest, not the LLC
events. The report therefore takes the LLC-miss attribution from the
bare-metal run in `results/host_bare_metal/` and everything else from the VM.

`results/` holds the measurement files the report was written from. Re-running
the stages overwrites them; on the same machine the numbers come back within
about 1–2 % (run-to-run noise), so the report's figures stay valid but will not
match a fresh run digit for digit. `script_btree.sh` at the top level changes into
`Hw__Additional_Files/` and works there; all paths below are relative to that folder.

**Requirements** (Ubuntu 24.04 and 22.04 tested). `./script_btree.sh setup`
installs the system packages itself with apt-get when it runs as root or with
passwordless sudo; otherwise install them first: `python3`, `python3-venv` (the
`python3.X-venv` package matching your python3), 
`python3-dbg`, `perf`, `git`, `perl`. The hardware flow is separate from the
benchmark script: `Hw__Additional_Files/hw/run_hw.sh` needs a C++ toolchain
(`g++`, `make`, `autoconf`, `flex`, `bison`) and builds Verilator from source
into `tools/` if none is on `PATH` (`VERILATOR_ROOT` may point at an existing
build instead).

**Virtual environments**: `./script_btree.sh setup` creates `.venv` (release)
and `.venv_dbg` (python3-dbg) inside this directory; both are git-ignored.
If they already exist one level up, the scripts use those.

Key numbers (course VM, CPython 3.12.15): baseline 3.11 s per loop, optimized
1.94 s, 1.60× faster (bare-metal cross-check: 5.06 s → 3.07 s, 1.65×); the
hardware unit answers the nsrch instruction in 7–9 cycles issue→writeback
(average 7.7, L1 line fetch included) and passes all 3 210 vectors in simulation.
(`results/optimized/compare_rigorous.txt`). The only code change is the in-node key
search: `diff -u benchmark/original/bm_btree/run_benchmark.py benchmark/optimized/bm_btree/run_benchmark.py`
(saved as `benchmark/btree_optimization.diff`).

All scripts are run from this folder and use the interpreters one level up:

```
cd btree   # the repository root
./script_btree.sh setup        # 1. environment setup and dependency installation
./script_btree.sh benchmark    # 2. benchmark execution: pyperformance, 10-process reference run, analysis, micro-benchmark
./script_btree.sh flamegraph   # 3. flame graph and performance data generation: perf stat, perf record, flame graphs (release + debug)
./script_btree.sh compare      # 4. post-optimization execution with comparison: generate, test, run, compare_to, flame graph, back-to-back timing
./script_btree.sh              # all four in order
Hw__Additional_Files/hw/run_hw.sh               # hardware: model check, vectors, block diagram, lint + simulate
cd "Hw__Additional_Files" && ../.venv/bin/python tests/test_btree_equivalence.py
```

## Reading the flame graphs

All flame graphs live in `Hw__Additional_Files/results/flamegraphs/` (baseline recorded by the `flamegraph` stage, optimized by the `compare`
stage that follows it, same settings). Open the `*_python.svg` files in a browser:
`baseline_release_python.svg` and `optimized_release_python.svg`. They show
Python functions only, rooted at `run_bench`, and scale to the window. Click a
frame to zoom into it, click the title to reset, use "Search" (top right) or
Ctrl-F to highlight a function such as `get_position`. Width = share of CPU
samples of that recording.

The `*_full.svg` files are the raw graphs with every CPython interpreter frame
(up to ~130 deep); keep them for the C-level detail, not for reading. The
`*.folded` files can be dropped onto https://www.speedscope.app for a
pan-and-zoom viewer. `results/flamegraphs/timing_back_to_back.txt` holds the pyperf
speed-up measured in the same session. See `results/flamegraphs/README.md`.
