# Node Search Unit (NSU) — hardware acceleration proposal for the btree benchmark

Files: `rtl/nsu_top.sv` (**the NSU**: execution unit behind one instruction,
streaming early-out design), `rtl/nsu_top_fixed.sv` + `rtl/nsu_core.sv` (the
fixed 31-lane design the NSU evolved from, kept as the reference, §5b),
`tb/tb_nsu.sv` and `tb/tb_nsu_fixed.sv` (self-checking testbenches),
`gen_vectors.py` + `model/nsu_model.py` (golden model and vectors from the real
benchmark tree), `run_hw.sh` (the whole hardware flow), `run_sim.sh` (Verilator
lint + simulation), `block_diagram_system.svg` (Figure 1, generated by
`make_block_diagram.py`), `sw/nsu_get_position.py` (software-side sketch).

The design is fitted to this benchmark on purpose: node blocks of 32 32-bit
entries (CLRS minimum degree t = 16 → at most 2t−1 = 31 keys per node), 32-bit
unsigned keys (the benchmark's keys are ints 0..199999), 16 lanes = one
64-byte cache line, no parameters, no options, no software-visible registers.

## 1. What is accelerated and why

Profiling the pyperformance `btree` benchmark showed that ~50 % of the timed
loop is one method, `BNode.get_position`: given a node's sorted keys, return
the index of the first key ≥ query. It is called 1.93 million times per loop,
compares 10.6 keys per call on average (20.5 million comparisons per loop),
and costs 1 668 ns per call in the interpreter. The software fix (binary
search in C over a plain key list) brought this to 513 ns per call and the
loop from 5.06 s to 3.07 s. Of the 513 ns, roughly 206 ns is the fixed cost of
a Python method call and the rest is the C search plus tuple/int unboxing.

The operation is a textbook accelerator target: fixed width and data
parallel (≤ 31 keys against one query, no dependence between lanes), sorted
input (once a key ≥ query has been seen, every later key is too, so the unit
can stop reading), tiny state (a query, a 5-bit count, a 5-bit running
position), trivially verifiable (its contract is `bisect_left`), and generic
("rank of a value in a sorted vector" is the primitive of every B-tree,
B+-tree, sorted-array and bucketed-index search) — the "ISA extension that is
not too workload-specific" the assignment asks for.

## 2. The instruction

```
nsrch rd, rs1, rs2
    rs1 : address of the node block (128 B aligned)
    rs2 : query key, 32-bit unsigned, in bits 31:0
    rd  : bit 8 = found, bits 4:0 = position, other bits 0
```

```
position = | { i < count : key[i] <  query } |        (0 … 31)   = bisect_left
found    =   ∃ i < count : key[i] == query
```

**Node block in memory** — 32 entries of 32 bits each = 128 bytes = exactly
two cache lines, 128 B aligned ("entry" = a 32-bit slot; not a machine word,
which is 16 or 32 bits depending on the ISA manual):

| entry | content |
|---|---|
| 0 | header: key count, number of valid keys (0..31) |
| 1 .. 31 | keys k0 .. k30, sorted ascending, unsigned |

Line 0 holds entries 0..15 (the header and k0..k14), line 1 entries 16..31
(k15..k30). Putting the count in the block is what lets the instruction take
only an address and a query: the unit reads the count itself, from entry 0 of
the first line.

**Key width.** 32-bit keys fit this benchmark (keys < 200,000) and most
indexes, and they halve the block (two lines instead of four) and the
comparators compared with 64-bit keys. Python ints outside 0 .. 2^32−1 take
the software path, so correctness never depends on the width. The 64-bit
variant is the same design with 8 lanes per line and a 4-line block; it was
built and measured first (7..12 cycles, average 8.7).

## 3. Interfaces

### 3.1 nsu_top (the NSU)

| port | width | dir | meaning |
|---|---|---|---|
| clk, rst_n | 1 | in | clock, async active-low reset |
| issue_valid | 1 | in | the execute stage issues nsrch |
| rs1_addr | 64 | in | node block address |
| rs2_query | 64 | in | query in bits 31:0 (upper half ignored) |
| busy | 1 | out | an instruction is in flight (one at a time) |
| mem_req_valid / mem_req_ready | 1 | out / in | L1 line port handshake |
| mem_req_addr | 64 | out | line address (rs1 + 64·j, j = 0..1) |
| mem_rsp_valid | 1 | in | line returned, in order |
| mem_rsp_data | 64 B (512 bits) | in | one cache line = 16 entries |
| rd_valid | 1 | out | result ready for writeback (one cycle) |
| rd_data | 64 | out | {found, position} |

The L1 port is read-only. Its data width is one cache line, 64 bytes, a design
choice; it says nothing about the host's bus widths.

### 3.2 Operating frequency

Stage 1 is a 32-bit magnitude comparator plus a 32-bit equality per lane,
16 lanes in parallel, plus the 5-bit valid-mask compares; the longest path is
a comparator followed by the 16-input OR that forms the boundary flag. Stage 2
is a 16-input popcount (adder tree), a 5-bit adder and a 16-input OR. Both
fit one cycle at **1.5 GHz and above in a 28 nm ASIC flow**, **~400 MHz on a
mid-range FPGA**. Control is not on the critical path. Fully synchronous,
single clock, asynchronous active-low reset.

## 4. Architecture (Figure 1, `block_diagram_system.svg`)

Reading `nsu_top.sv`, top to bottom, the four blocks of Figure 1:
(1) **Control** — registers that keep rs1/rs2 for the search, a two-state FSM, the request
and response counters, the stop/drain logic; (2) **line compare** — 16 lanes
on the arriving line with the valid mask, registered as S1; (3)
**accumulate** — popcount-16 adder tree, 5-bit running position, running
found, registered as S2; (4) the **rd register** with `rd_valid` for
writeback. No parameters, no `for` in `always` blocks (one `generate` for the
lanes and the adder tree).

1. **Issue.** The execute stage presents rs1 and rs2 with `issue_valid`; the
   unit copies them into its own registers (the pipeline's operand buses
   change next cycle) and raises `busy`.
2. **Fetch.** Two line requests, rs1 and rs1 + 64, leave back to back; the
   lines return in order. Entry 0 of line 0, the header, loads the key-count
   register (for line 0 the count is taken live from the arriving data).
3. **Line compare (S1), every arriving line.** Lane k holds entry k of the
   line. `valid[k] = (1 ≤ 16·line + k ≤ count)` masks out the header entry and
   the slots beyond the count. `lt[k] = valid[k] & (key < query)`,
   `eq[k] = valid[k] & (key == query)`. The early-exit decision is taken from
   the same lane outputs: `boundary = any(valid & ~lt)` — some valid key in
   this line is ≥ query, so the first key ≥ query is in this line and no later
   line can change the answer — and `last = (line == count >> 4)`, the last
   line that holds keys. All four are registered in S1.
4. **Accumulate (S2).** The adder tree decides nothing; it only counts:
   `popcount(lt[15:0])` is the number of keys of this line that are < query
   (16 → 5 reduction: 8 half adders, 4 adders, 2 adders, 1 adder). A 5-bit
   adder adds it to the running position; `found |= any(eq[15:0])` through a
   16-input OR. S2 is the running result; after the boundary line, position =
   number of keys < query over the whole node = `bisect_left`. `found` alone
   never stops the search: an equal key is also ≥ query, so it sets
   `boundary`, and the position is still needed.
5. **Early exit.** When `boundary | last` is set, the S2 value after that line
   is final: `rd = {found, position}` is written with `rd_valid`, Control
   stops issuing requests, a line already requested is drained and ignored,
   and `busy` drops when the last requested line is in.

Measured in simulation with a 3-cycle L1 latency and a ready signal that
stalls one cycle in four, over all 3 210 vectors: **7..9 cycles from issue to
`rd_valid`, average 7.7**; busy 9.3 cycles per instruction (the drain);
latency histogram 7: 1 707 · 8: 824 · 9: 679. On the real tree the boundary
falls in line 0 (header + k0..k14) for 53 % of the searches and in line 1 for
47 % — 1.47 of the 2 lines are needed on average.

## 5. Software interface and required software changes

### 5.1 Data layout

Each node keeps its keys in a 32-entry `array.array('I')` (32-bit unsigned
entries): entry 0 = key count, entries 1..31 = keys, allocated 128 B aligned.
This replaces the plain `keys` list of the optimized benchmark; the
`(key, record)` tuples stay as they are. Maintaining it is the same one-line
mirroring already present in the optimized code plus keeping entry 0 equal to
`len(items)` (`sw/nsu_get_position.py`).

**Where a node lives today (measured, `node_memory_breakdown.txt`).** A Python
node is not one chunk. A typical 15-item leaf is ~34 separate heap objects:
the BNode (56 B), its `items` and `keys` lists (176 B each), 15 `(key, record)`
tuples (56 B each), 15 int key objects (28 B each) and 15 Records (~380 B each
with their `__dict__`), about 7.4 KB in total scattered over the heap and
linked by pointers; an internal node adds a `nodes` list (184 B). The
hardware node block replaces only the `keys` list: one contiguous 128 B
array, count + 31 keys, 128 B aligned, so the unit reads it with two line
requests and never follows a pointer. For the whole tree that is 10,150 × 128 B
= 1.3 MB of blocks, comfortably L2/LLC resident, while the tuples and records
stay where they are.

### 5.2 Integration

* **ISA.** One new R-type instruction, `nsrch rd, rs1, rs2`, decoded to the
  NSU as a multi-cycle functional unit beside the ALU and LSU. It reads
  memory through the L1 D-cache port (read only), so it behaves like a load
  with a variable 7..9-cycle latency: the scoreboard holds rd until
  `rd_valid`, and the usual load-ordering rules apply (stores to the node
  block before the `nsrch` must be visible to it — the L1 provides that).
  `busy` stays high a cycle or two after `rd_valid` while the unit drains a
  line it no longer needs; a second `nsrch` waits for it.
* **Compiler / runtime.** A C extension exposes `nsrch(node_addr, query)`
  through an inline-asm intrinsic; `BNode.get_position_hw` calls it with the
  array's buffer address and falls back to `bisect_left` when the instruction
  is absent or the key is outside 0 .. 2^32−1.
* **No driver, no memory-mapped registers, no polling, no pinning.** The
  node block is ordinary user memory; the instruction reads it like a load.

### 5.3 Acceleration estimate (assumptions stated)

Per loop: 1.93 M calls; 2.47 s in the search today; 2.57 s in everything else.

| variant | ns / node search | search time / loop | loop time | vs baseline |
|---|---|---|---|---|
| baseline linear scan (measured) | 1 668 | 2.47 s | 5.06 s | — |
| bisect on keys list (measured) | 513 | 0.79 s | 3.07 s | 1.65× |
| nsrch instruction, L1 hit (estimate) | ≈ 210 | 0.41 s | ≈ 2.98 s | ≈ 1.69× |
| theoretical floor (search cost → 0) | 0 | 0 | 2.57 s | 1.96× |

Assumptions: the interpreter call overhead (206 ns, measured) is unchanged;
the node block hits L1/L2 (measured L1 miss rate 2.2 %, IPC 1.44 over the whole
loop). Working set: the tree structure is 19–23 MB and the records 68 MB, so
the total does not fit the 20 MB LLC — the 10 M LLC misses per loop belong to
the garbage collector walking the heap and to the shuffled-order inserts
(measured per phase, `results/baseline/perf_phase_counters_release.txt`) — but
the node search never touches a record (200k lookups without reading records:
0.4 M misses), and its hot set (tuples + keys 16 MB, 19 MB with lists and BNodes;
1.3 MB of key blocks for the NSU) stays resident. 7.7 cycles at 2.4 GHz ≈ 3 ns;
no other change to the benchmark.

Conclusion: under CPython the instruction removes essentially all of the
*search* cost, but Amdahl's law caps the loop near 1.7× because the remaining
Python work (allocation, tuple handling, recursion, GC) is untouched. The
unit's value is highest where the caller is compiled code: there the same
node search costs 20–40 cycles of branchy binary search against 7–9 cycles
here, of which 2 are compute and the rest is the line fetch — the
memory-bound regime the textbook B-tree analysis assumes.

## 5b. The fixed 31-lane design it evolved from (`rtl/nsu_top_fixed.sv` + `rtl/nsu_core.sv`)

The first version of the unit waits for both lines, holds the 31 keys in
registers and compares them all at once: `nsu_core.sv` is one `generate`
block of 31 identical lanes (`en[i] & (key[i] < query)`,
`en[i] & (key[i] == query)`, `en[i] = (count > i)`), a stage-1 register for
the two 31-bit masks, an explicit adder tree (15 + 7 + 3 + 1 small adders
plus leftovers) and a 31-input OR, a stage-2 register; `nsu_top_fixed.sv`
wraps it with Control, 31 key registers fed from the two lines, and the rd
register. It is simpler to reason about and has a constant latency, but it
waits for a line it often does not need and spends 31 comparators where 16
do the same work. Both designs run the same testbench conditions (3-cycle L1
latency, ready stalled 1 in 4, all 3 210 vectors correct):

| | **NSU (streaming early-out)** | fixed 31-lane design |
|---|---|---|
| issue → rd_valid | **7..9 cycles, average 7.7** | 10 cycles (11 with a stall) |
| unit busy per instruction | 9.3 (drains a requested line) | 10 |
| line requests per search | 2.00 — both leave before line 0 returns | 2 |
| comparators (32-bit `<` and `==`) | 16 pairs | 31 pairs |
| key storage | none, compared on arrival | 31 × 32-bit registers |
| compute after the last needed line | 2 cycles (S1 + S2) | 2 cycles |
| area (28 nm, estimate) | ≈ 3.5 k gate-eq. + ≈ 220 flops | ≈ 6–7 k gate-eq. + ≈ 1.2 k flops |
| result file | `sim_result.txt` | `sim_result_fixed.txt` |

Bandwidth is the same: with back-to-back requests and a 3-cycle L1, both
requests leave before the first line is back. Requesting the second line only
when needed would cut traffic to ~1.5 lines per search but add the memory
latency to the 47 % of searches that need it and end up slower on average;
the current policy trades a little L1 bandwidth for latency. Under CPython
the 2–3 cycle (≈ 1 ns) difference is invisible against the 206 ns call
overhead; for compiled callers it is a 1.3× lower search latency from a 2×
smaller comparator array.

## 6. Performance / area / power trade-offs

| block | estimate (28 nm) |
|---|---|
| 16 × (32-bit `<` + 32-bit `==`) | ≈ 16 × 180 ≈ 2.9 k gate-eq. |
| valid mask, popcount-16 adder tree, 5-bit adder, OR-16 | ≈ 250 gate-eq. |
| Control: FSM, request/response counters, address adder, boundary/last logic | ≈ 400 gate-eq. |
| flops: rs1 copy 64, rs2 copy 32, count 5, S1 35, S2 6, rd 65, FSM + counters ≈ 15 | ≈ 220 flops |
| total | ≈ 3.5 k gate-eq. + ≈ 220 flops ≈ 0.003–0.005 mm² |

* **Frequency vs latency**: 2 pipeline stages per line give 1.5 GHz and
  above; the instruction latency is dominated by the line fetches (7..9
  cycles), not by the compute (2 cycles after the last needed line).
* **Key width**: 32-bit keys fit this benchmark and most indexes and halve
  the block and the comparators compared with 64-bit keys; keys ≥ 2^32 take
  the software path. The 64-bit variant (8 lanes, 4 lines) measured 7..12
  cycles, average 8.7.
* **Early exit vs bandwidth**: both lines are requested up front, so latency
  is minimal and control trivial, at the cost of fetching a line that is then
  discarded (0.5 of 2 on average). A count-aware or one-at-a-time fetch would
  save that bandwidth and cost latency; not worth it at this call rate.
* **Fitted, not configurable**: 32-bit keys, 16 lanes = one 64 B line,
  32-entry blocks; matches this benchmark exactly.
* **Throughput**: one instruction in flight at a time; a second `nsrch` waits
  for `busy`. At the interpreter's ~2 M searches/s the unit idles > 99.9 % of
  cycles, so no overlap is needed; compiled callers or a future tree-walk
  unit that chains node searches would want it.
* **Power**: 16 comparators toggle once per arriving line; clock-gated,
  dynamic power is well under 1 mW at 1 GHz when active, microwatts on
  average; leakage a few µW.
* **Memory traffic**: the node's two lines, the same lines the CPU would
  touch.

## 7. Verification

`run_hw.sh` runs the whole flow (model check, vectors, node layout, block
diagram, Verilator build if needed, both simulations). `run_sim.sh` lints the
RTL with Verilator `-Wall` (clean) and runs the testbenches:

* **`tb/tb_nsu.sv` (the NSU)** issues one `nsrch` per vector to `nsu_top`
  against a memory model holding each node block (key count in entry 0, keys
  in entries 1..31, 32-bit entries, 16 per line; 3-cycle latency, ready
  stalled 1 cycle in 4) and checks `rd_data` for all 3 210 vectors: 3 000 real
  (node, query) pairs recorded from the benchmark's tree during lookups,
  inserts and deletes; 18 directed corner cases (empty node, single key, full
  node with the query below/at/above every boundary, 32-bit extremes, count
  smaller than filled lanes); 192 random nodes covering every count 0..31. It
  also records the latency histogram, the busy time and the requests issued
  per instruction.
* **`tb/tb_nsu_fixed.sv` (reference design)** — phase A: the same
  per-instruction check on `nsu_top_fixed`; phase B: `nsu_core` fed
  back-to-back, one vector per cycle, checked at the 2-cycle latency.

Result: `sim_result.txt` — `PASS: all 3210 vectors correct`, 7..9 cycles,
average 7.7; `sim_result_fixed.txt` — `PASS`, 10–11 cycles. Expected values
come from `model/nsu_model.py`, itself checked against `bisect_left` on every
vector. Not done, as the assignment permits: synthesis, place-and-route, FPGA
or silicon test; area/frequency/power are estimates.
